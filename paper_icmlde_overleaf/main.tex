\begin{abstract}
A user's interests extend across media: the same preference can appear as a film theme, a book topic, a musical artist, or a learning goal. Conventional recommenders operate within single-domain silos and cannot connect these signals. This paper presents a real-time adaptive cross-media recommender that maps movies, books, and music into one normalized catalog and ranks them with a hybrid score. The backend combines Sentence-BERT metadata embeddings with Qdrant approximate nearest-neighbor search, deterministic creator-aware search, MySQL interaction logging, exponential moving average (EMA) session adaptation, LightGCN collaborative filtering, and knowledge-graph (KG) profile-aware reranking; a React frontend exposes search, filters, per-signal score explanations, and feedback. Each component covers a distinct requirement: embeddings handle heterogeneous text and cold start, creator matching protects person queries, EMA follows short-term preference drift, LightGCN captures collaborative preference, and the KG links domains through shared creator, genre, age, profession, and interest entities. \section{Introduction}
\label{sec:introduction}
\email{g\_krishnapriya@cb.amrita.edu (Krishna Priya G.), pbsk@cb.amrita.edu (Bagavathi Sivakumar P.)}
Recommendation systems are now the main interface through which users discover movies, songs, books, learning resources, and other digital content. Most deployed systems, however, remain domain-specific: a movie platform recommends films, a music platform recommends tracks, and a book platform recommends books. This separation is practical for platform owners, but it does not reflect how human interest works. A user interested in science fiction may enjoy a film such as \emph{Interstellar}, a novel about space exploration, a soundtrack with a similar emotional tone, and educational content on astronomy. A useful recommender should therefore connect these signals across media types, so that recommendations follow the user's preferences rather than the boundaries of a single medium.

This paper presents a unified recommendation pipeline for three domains: movies, books, and music. Every item, whatever its medium, is mapped to a common schema with fields such as a global identifier, content type, title, description, creators, categories, release date, popularity, rating, metadata, and embedding text. This representation allows heterogeneous datasets to be indexed in a single semantic retrieval layer in which every item is an entity of the same kind. On top of this layer, the system logs user interactions and personalizes results with both an immediate (per-event) method and a periodically trained method. The goal is not only to retrieve semantically similar content, but also to combine it with recommendations that adapt to user behavior over time.

Three technical directions motivate the implementation. Sentence-BERT allows items from different domains to be compared through their textual descriptions \cite{reimers2019sbert}; LightGCN learns collaborative preference from the user--item interaction graph \cite{he2020lightgcn}; and Qdrant provides low-latency nearest-neighbor retrieval \cite{qdrant}. The FastAPI \cite{fastapi} backend integrates Qdrant for retrieval, MySQL for storage and interaction logging, a PyTorch LightGCN model for reranking, an exponential moving average (EMA) of item embeddings for session adaptation, and an in-memory knowledge graph (KG) for entity-aware profile scoring.

The research gap is that these capabilities are rarely implemented together in a single working multi-domain pipeline. Graph-based models are usually benchmarked on single-domain interaction datasets; semantic systems retrieve content by meaning rather than by the user's preferences; cross-domain approaches commonly transfer between two domains instead of normalizing several domains into one catalog; and real-time personalization is usually treated separately from graph learning.

The design addresses heterogeneous metadata, the item cold-start problem, session-level preference drift, hybrid score fusion, people-based search over actors, directors, authors, and singers, and age- and profession-aware scoring without private social data.

The contributions of this paper are threefold:
\begin{enumerate}
    \item An integrated movie, book, and music platform that supports semantic, creator-aware, and flexible search through a unified catalog and web application.

    \item A hybrid ranking model that combines Sentence-BERT/Qdrant retrieval, EMA-based personalization, LightGCN graph scoring, and knowledge-graph profile scoring.

    \item A quantitative evaluation on three large public interaction datasets, comprising single-signal baselines, an ablation of every signal, validation-based weight selection, and latency measurements, complemented by scenario-level tests of the working prototype.
\end{enumerate}

\section{Discussion of Related Work and Novelty}
\label{sec:discussion}
Recommendation methods include collaborative filtering, content-based recommendation, hybrid recommendation, graph neural collaborative filtering, semantic retrieval, knowledge-graph recommendation, adaptive approaches, and cross-domain transfer. Collaborative filtering learns from behavior and content-based recommendation from item metadata, while hybrid approaches combine the two to reduce the cold-start problem \cite{zhang2019deep}.
Neural Graph Collaborative Filtering (NGCF) applies graph convolution to the user--item interaction graph; LightGCN simplifies NGCF by removing feature transformations and non-linear activations and keeping only neighborhood-based embedding propagation \cite{wang2019ngcf,he2020lightgcn}. In this work LightGCN is used as a collaborative reranking signal rather than as the candidate generator: semantic retrieval first finds relevant cross-media candidates, and the graph-derived representations then add a signal for users with sufficient interaction history. Sequential recommenders such as SASRec model the order of user actions and are usually evaluated offline within a single domain \cite{kang2018sasrec}; because they play a different role from cross-media retrieval, a hybrid ranking pipeline is adopted here instead.

Semantic embedding methods compute item similarity before many user interactions exist. Sentence-BERT is practical because it produces sentence embeddings that can be compared directly by cosine similarity \cite{reimers2019sbert}. Here, each item is converted into an embedding text that combines its title, categories, description, and creators, which places movies, books, and songs in a shared vector space.

Knowledge-graph systems such as KGAT and RippleNet connect users, items, and entities through relations such as acted-in, directed-by, written-by, and belongs-to-genre \cite{wang2019kgat,wang2018ripplenet}. The present implementation builds an in-memory KG from the unified catalog and uses it for entity-proximity scoring. Cross-domain research supports preference transfer between domains, although many works still focus on transfer between two domains \cite{zang2022cross}; a recent survey broadens this scope to multi-domain and task-guided transfer \cite{zhang2025survey}. Large language models augmented with graph structure have also been explored for relevance and explanation generation \cite{wu2024llmrec}.

Recent work has moved in two directions that are directly relevant here. Knowledge-aware graph recommenders combine LightGCN-style propagation with knowledge graphs: LGKAT adds a personalized knowledge-aware attention sub-network to LightGCN and is evaluated separately on movie, book, music, and restaurant data \cite{hassanzadeh2025lgkat}, and LightKG simplifies the graph neural network of knowledge-aware recommenders to reduce training cost on sparse data \cite{li2025lightkg}. Cross-domain recommenders increasingly use large language models as a semantic bridge between domains: LLMCDSR uses an LLM to generate pseudo-interactions and injects collaborative information into textual item features \cite{xin2025llmcdsr}, LLM4CDSR builds unified LLM-based item representations and hierarchical user profiles across domains \cite{liu2025llm4cdsr}, LeCDSR likewise enhances cross-domain sequential recommendation with an LLM \cite{wang2026lecdsr}, and KLLMRec augments multi-domain recommendation with LLM-derived knowledge \cite{li2026kllmrec}.

Recent studies from Amrita Vishwa Vidyapeetham have addressed several recommendation challenges, including cold-start prediction, optimization of collaborative filtering, sparse interaction data, dual-feedback personalization, and community-aware recommendation \cite{amrita2023densenet,amrita2023adamvrgo,amrita2024sparse,amrita2025dualfeedback,amrita2026svd}. These studies, however, do not address the integration of heterogeneous media into a common recommendation pipeline. In the proposed system, movies, books, and music share one catalog schema and pass through shared retrieval, personalization, and reranking stages. The contribution therefore lies in cross-media integration rather than in another standalone model.

The novelty of this work is not a new neural layer; it is the combination of mature methods within one working pipeline, each covering a distinct requirement. Sentence-BERT provides cross-domain semantic understanding, Qdrant low-latency vector retrieval, MySQL durable interaction memory, EMA immediate handling of preference drift, LightGCN collaborative preference propagation, and the knowledge graph entity- and profile-level reasoning. Related systems usually emphasize one of these capabilities; the proposed system combines all of them behind a clear input--output API with a path for adding new domains.
Unlike a traditional hybrid recommender, which fuses content and collaborative scores from models trained separately in each domain, the proposed system first maps heterogeneous media into one common schema that serves vector search, creator lookup, graph construction, API responses, and the frontend. Cross-media recommendation is therefore treated as both a data-modeling problem and a ranking problem. The system also separates immediate from delayed personalization: EMA reacts to a single like, skip, or bookmark, whereas LightGCN is retrained once enough new interactions have accumulated. This division is practical because sessions change quickly while graph training is comparatively expensive.

\section{Implementation}
\label{sec:implementation}
\subsection{Web application system}
The implemented system is a modular web recommendation product. The frontend provides user profile selection, natural-language search, content-type filters, recommendation cards, score-signal display, detail views, similar-item search, and interaction buttons. The backend exposes recommendation and interaction APIs. The data pipeline preprocesses heterogeneous datasets into a common catalog, generates embeddings, uploads vectors to Qdrant, stores content and user interactions in MySQL, trains LightGCN artifacts from positive interaction logs, and exposes KG-profile scoring at query time.

The request flow begins when the user enters a query such as \emph{space adventure with aliens}, \emph{James Cameron}, or \emph{business analytics and learning}. The request contains the query, an optional user identifier, an optional content-type filter, and the desired number of results $K$. The backend validates the request with Pydantic, checks for direct creator matches, embeds the query, retrieves vector candidates from Qdrant, applies MySQL-backed personalization when a user is known, blends all scores, and returns the results as JSON. The frontend displays each result's title, domain, creators, categories, and score bars, and lets the user give feedback, which is sent back to the backend and used in subsequent rankings.

    \caption{System architecture of the proposed cross-media recommender.}
    \label{fig:architecture}

Figure~\ref{fig:architecture} shows the four layers of the system. The retrieval layer (Sentence-BERT encoding and Qdrant approximate nearest-neighbor search), the storage layer (MySQL catalog and interaction logs), the personalization layer (EMA updates and periodically retrained LightGCN embeddings), and the presentation layer (FastAPI endpoints consumed by the React frontend) are separated so that each component can be tested on its own. Qdrant search runs at request time, the EMA profile is updated immediately after each feedback event, and LightGCN is retrained periodically.
The pipeline produces explicit intermediate artifacts: normalized catalog rows, embedding texts, dense vectors, Qdrant payloads, MySQL interaction logs, and exported graph embeddings. These artifacts make experiments more reproducible, because an error can be traced to a single stage instead of being hidden inside one end-to-end model.

\subsection{Data sources and unified catalog}
The central implementation decision is to map every domain to one unified schema.
Movies use TMDb metadata and credits \cite{tmdb}; books use a Google Books-style dataset with optional enrichment from the Open Library APIs \cite{openlibrary}; and music uses a Kaggle songs dataset with optional enrichment from the MusicBrainz API \cite{musicbrainz}. The common fields are a global identifier, content type, source identifier, title, description, creators, categories, release date, popularity, rating, metadata text, embedding text, and a text hash.

For movies, preprocessing combines the title, overview, genres, keywords, directors, and main cast. For books, the author field is mapped to the shared \emph{creators} field, while categories and descriptions form the semantic text. For music, the track artist and album are mapped to the creators and metadata fields. This allows the same search logic to handle actors, directors, authors, and singers. The metadata text is a richer string used for inspection and storage, whereas the embedding text is a clean natural-language string used for encoding. A SHA-256 hash of the embedding text allows embeddings from a previous build to be reused when a row has not changed.

The catalog separates each item's source identifier from its global identifier, so that raw identifiers from different datasets cannot collide. The content-type field acts as the domain switch for filters, API responses, KG nodes, and frontend badges. Ratings and popularity are optional, which keeps the schema robust when new domains are added.

Extensible search means that a new domain does not require a new recommender pipeline. Let each domain $d \in \mathcal{D}$ provide a mapper $\phi_d(x)$ from a raw row $x$ into the shared item representation $r_i$. The catalog is
\begin{equation}
    \mathcal{C}=\bigcup_{d\in\mathcal{D}}\{\phi_d(x):x\in X_d\},
    \quad
    r_i=(id,type,title,desc,creators,categories,text_i).
    \label{eq:catalog_union}
\end{equation}
When a further domain such as courses, podcasts, games, or short videos is added, only $\phi_d$ has to be defined; embedding, vector search, KG scoring, the API response, and frontend rendering remain unchanged.

\subsection{Semantic embedding and vector search}
The semantic retrieval layer uses Sentence-BERT, specifically the compact all-MiniLM-L6-v2 model, to convert item metadata into dense 384-dimensional vectors \cite{reimers2019sbert}. The dimension is fixed by the output layer of this model rather than being a free hyperparameter; keeping item embeddings, query embeddings, and user profile vectors (Section~\ref{sec:ema}) in the same space allows cosine similarity to be computed directly between users, items, and queries without an additional projection layer. The embedding text of each item concatenates its title, categories, description, and creators into one natural-language string. Let $\mathbf{e}_i \in \mathbb{R}^{384}$ be the embedding of item $i$ and $\mathbf{q} \in \mathbb{R}^{384}$ the encoded query. The semantic similarity score is
\begin{equation}
    S_{\mathit{sem}}(i,q)=
    \frac{\mathbf{e}_i^\top \mathbf{q}}{\|\mathbf{e}_i\|\,\|\mathbf{q}\|}.
    \label{eq:cosine}
\end{equation}
At retrieval time, Qdrant uses this cosine similarity for approximate nearest-neighbor search and returns the top-$K$ results with their scores. An optional content-type filter lets users search all domains or only one, such as movies, books, or music. Because the item payload is stored in Qdrant, the title, description, creators, categories, popularity, rating, and score are all available from a single request.

The semantic layer enables cold-start and cross-domain retrieval: a new item can be recommended from its metadata alone, without any interactions, and the same query can retrieve a movie, a book, or a song whose metadata is semantically similar.

Vector search is used for candidate generation, not for the final ranking. Qdrant quickly retrieves semantically similar items, and the reranking stage then accounts for user preference, creator intent, graph information, and KG/profile relevance.

\subsection{Person-aware search over creators}
\label{sec:person}
Users of recommendation interfaces frequently search for people rather than topics. Vector search alone does not distinguish names from generic text and may miss an exact match in the catalog.
The backend therefore looks for exact, prefix, and substring matches on normalized creator names before running the semantic search. Up to five items directly associated with the person are placed first, and semantic results are appended after deduplication on the global identifier.
This matters because the intent behind a name is not always captured by dense similarity. A search for James Cameron should prioritize his films; a search for Taylor Swift should return her music without duplicates, while still allowing cross-media hits where the metadata supports them. The shared creators field is both the search field and a source of graph entities.
Creator search is deterministic: exact matches have the highest priority, followed by prefix matches and then substring matches.

\subsection{Interaction logging and EMA adaptation}
\label{sec:ema}
The backend records user interactions through a dedicated API and stores them in MySQL. Each event type carries a signed weight $w$: view $0.4$, click $0.6$, like $1.0$, bookmark $1.0$, complete $1.2$, and skip $-1.0$; an explicit rating $r\in[1,5]$ is mapped to $w=(r-3)/2$, so that four and five stars are positive, three stars is neutral, and one or two stars are negative. Events with $w=0$ are ignored.

Let $\mathbf{u}_t \in \mathbb{R}^{384}$ be the user's profile vector, kept in the same Sentence-BERT space as the item embeddings so that $\mathbf{u}_t$ and $\mathbf{e}_i$ are directly comparable, and let $\alpha\in(0,1)$ be the smoothing factor ($\alpha=0.25$). An event with weight $w$ on item $i$ moves the profile by a step $\eta=\alpha\min(|w|,1)$ toward $\mathbf{e}_i$ when $w>0$ and toward $-\mathbf{e}_i$ when $w<0$:
\begin{equation}
    \tilde{\mathbf{u}}_{t+1}=(1-\eta)\,\mathbf{u}_t+\eta\,\mathrm{sign}(w)\,\mathbf{e}_i,
    \qquad
    \mathbf{u}_{t+1}=\tilde{\mathbf{u}}_{t+1}/\|\tilde{\mathbf{u}}_{t+1}\|.
    \label{eq:ema_update}
\end{equation}
The profile is empty until the user's first non-neutral event on an embedded item, which initializes it to $\mathbf{u}_1=\mathrm{sign}(w)\,\mathbf{e}_i$; a user with no events therefore receives no EMA score. Likes, bookmarks, and completions thus pull the profile toward the item, a skip or low rating pushes it away from the item, and weak signals such as views move it less. Re-normalization after every update keeps the profile on the unit sphere, so repeated skips cannot shrink it to zero. The EMA score of a candidate item $i$ is
\begin{equation}
    S_{\mathit{ema}}(i,u)=
    \frac{\mathbf{e}_i^\top\mathbf{u}_t}{\|\mathbf{e}_i\|\,\|\mathbf{u}_t\|}.
    \label{eq:ema_score}
\end{equation}
EMA provides lightweight real-time adaptation without retraining the graph model after every click, which suits session-level changes such as a user temporarily moving from entertainment to learning content. More complex online learning could update model parameters continuously, but EMA updates only one vector per user and is cheap enough to run on every event.

\subsection{Graph collaborative filtering with LightGCN}
Semantic retrieval captures item similarity but not collaborative behavior. The system therefore includes a PyTorch LightGCN model trained on the interaction log; the exported user and item embeddings are used for reranking. An interaction is treated as positive, and becomes an edge of the training graph, when its event weight is positive ($w>0$). Repeated events on the same user--item pair are merged into a single unweighted edge, and skips and low ratings are excluded from the graph rather than used as explicit negatives.

LightGCN represents users and items as nodes in a bipartite interaction graph $\mathcal{G}=(\mathcal{U}\cup\mathcal{I},\mathcal{E})$, where each edge $(u,i)\in\mathcal{E}$ corresponds to a positive interaction. Let $\mathbf{e}^{(0)}_u$ and $\mathbf{e}^{(0)}_i$ be the initial learnable embeddings. The $\ell$-th layer propagation rule is
\begin{equation}
    \mathbf{e}^{(\ell)}_u =
    \sum_{i\in\mathcal{N}_u}
    \frac{\mathbf{e}^{(\ell-1)}_i}{\sqrt{|\mathcal{N}_u|}\sqrt{|\mathcal{N}_i|}},
    \quad
    \mathbf{e}^{(\ell)}_i =
    \sum_{u\in\mathcal{N}_i}
    \frac{\mathbf{e}^{(\ell-1)}_u}{\sqrt{|\mathcal{N}_i|}\sqrt{|\mathcal{N}_u|}}.
    \label{eq:lightgcn_prop}
\end{equation}
After $L$ propagation layers, the final embedding is the mean over all layers:
\begin{equation}
    \mathbf{e}_u=\frac{1}{L+1}\sum_{\ell=0}^{L}\mathbf{e}^{(\ell)}_u,
    \quad
    \mathbf{e}_i=\frac{1}{L+1}\sum_{\ell=0}^{L}\mathbf{e}^{(\ell)}_i.
    \label{eq:lightgcn_avg}
\end{equation}
The model is trained with the Bayesian Personalized Ranking (BPR) loss:
\begin{equation}
    \mathcal{L}_{\mathrm{BPR}}=
    -\sum_{(u,i,j)\in\mathcal{D}}\ln\sigma(\hat{y}_{ui}-\hat{y}_{uj})
    +\lambda\|\Theta\|^2,
    \label{eq:bpr}
\end{equation}
where $\hat{y}_{ui}=\mathbf{e}_u^\top\mathbf{e}_i$, $\Theta$ denotes the layer-0 embeddings of the batch, and $j$ is a negative item. For every sampled positive pair $(u,i)$, one negative $j$ is drawn uniformly from the catalog and redrawn if $(u,j)$ is itself a positive. BPR is used instead of a pointwise loss such as mean-squared error or binary cross-entropy because the signal is implicit and positive-only, with no reliable negative label for an item the user has simply not seen; it optimizes the pairwise ranking order directly and is the standard objective for LightGCN and related graph collaborative filtering models \cite{he2020lightgcn,wang2019ngcf}. The training settings (embedding size, number of layers, optimizer, batch size, and epoch budget) are listed in Section~\ref{sec:setup}. At inference time, user and item embeddings are $\ell_2$-normalized, and the graph compatibility score is their cosine similarity:
\begin{equation}
    S_{\mathit{graph}}(i,u)=\frac{\mathbf{e}_u^\top\mathbf{e}_i}{\|\mathbf{e}_u\|\,\|\mathbf{e}_i\|}.
    \label{eq:graph_score}
\end{equation}

The graph stage is a reranker rather than a candidate generator. Semantic retrieval supports cold-start discovery, while LightGCN is strongest when both user and item appear in the interaction graph. If a graph score is unavailable, the candidate can still be ranked using semantic, EMA, KG, and profile signals.

\subsection{Knowledge graph and profile-aware scoring}
The system includes an in-memory knowledge graph built directly from the processed catalog, without a separate graph database. It is constructed in three steps.

\emph{(i) Entities.} Every catalog item becomes an item node typed by its content type (Movie, Book, or Song). All text is Unicode-normalized and case-folded. Each entry of the creators field becomes a Creator node, each entry of the categories field a Genre/topic node, and every alphanumeric token of at least three characters in the title, description, creators, categories, and content type becomes a term entity of the item. Each user becomes a User node, and the declared profile attributes become Profession, Age Group, and Interest/Skill nodes.

\emph{(ii) Relations.} Items are linked to creators by directed\_by, written\_by, or performed\_by, according to the content type, and to genres by belongs\_to\_genre. Users are linked to items by liked, bookmarked, or completed when the event weight is positive (these edges also form the LightGCN training graph), and to their profile nodes. Each profession and age group is expanded into a fixed list of related topic terms (related\_to\_profession and suitable\_for; e.g., \emph{data analyst} $\rightarrow$ data, analytics, business, statistics, technology, science), and an age group may also carry a list of unsuitable terms (e.g., \emph{family} $\rightarrow$ horror, crime, thriller, war).

\emph{(iii) Paths.} A user reaches an item through a length-two path that passes through a shared entity: a query term, a profile term, a creator, or a genre. Because these entity namespaces are shared by all domains, the same path can end at a movie, a book, or a song (Fig.~\ref{fig:knowledge_graph}):
\begin{equation}
    P(u,i)=\{u\rightarrow e\rightarrow i:\;
    e\in \mathcal{E}_{\mathit{query}}\cup\mathcal{E}_{\mathit{creator}}\cup\mathcal{E}_{\mathit{genre}}\cup\mathcal{E}_{\mathit{profile}}\}.
    \label{eq:paths}
\end{equation}
Paths are not enumerated explicitly; both scores below count them through set intersections, which keeps scoring linear in the number of candidate items.

\begin{figure}[t]
    \centering
    \includegraphics[width=0.8\textwidth]{di.png}
    \caption{Knowledge graph used for profile-aware cross-media recommendation.}
    \label{fig:knowledge_graph}
\end{figure}

The KG score counts the paths through query-term entities. Let $\mathcal{T}(q)$ be the term set of query $q$ and $\mathcal{T}(i)$ the term set of item $i$; then
\begin{equation}
    S_{\mathit{kg}}(i,q)=
    \min\!\left(1,\frac{|\mathcal{T}(q)\cap\mathcal{T}(i)|}
    {\max(3,|\mathcal{T}(q)|)}\right),
    \label{eq:kg_score}
\end{equation}
where the floor of three in the denominator prevents a one- or two-word query from reaching the maximum score through a single shared term.
The profile score rewards items that align with the user's declared age group, profession, interests, and skills, while penalizing categories flagged as unsuitable:
\begin{equation}
    S_{\mathit{profile}}(i,u)=
    \sum_{t\in\mathcal{P}_{+}(u)} \delta(t,i)w_{+}
    -\sum_{t\in\mathcal{P}_{-}(u)} \delta(t,i)w_{-}
    +\mathbf{1}[\mathrm{pref}(u)=\mathrm{type}(i)]w_c.
    \label{eq:profile_score}
\end{equation}
Here $\mathcal{P}_{+}(u)$ contains the user's interests, skills, and the terms expanded from the profession and age group, $\mathcal{P}_{-}(u)$ the unsuitable terms, $\delta(t,i)=1$ if term $t$ occurs in the text of item $i$, $\mathrm{pref}(u)$ the user's preferred content types, $w_+=0.16$, $w_-=0.25$, and $w_c=0.15$. The score is clipped to $[-1,1]$. The profile relies only on declared, consent-based attributes and avoids scraping private social-media data.

\subsection{Recommendation pipeline and algorithms}
The recommendation pipeline is an ordered algorithm rather than a single monolithic model. Given a request $(q,u,K,\mathit{type})$, the backend validates it, normalizes the query and the domain filter, reserves exact creator matches when available, embeds the query with Sentence-BERT, retrieves Qdrant candidates, removes duplicates, applies the optional type filter, adds the EMA, LightGCN, KG, and profile scores when user context is available, and sorts the candidates by the hybrid score
\begin{equation}
    S(i,u,q)=S_{\mathit{sem}}(i,q)+
    \lambda_gS_{\mathit{graph}}(i,u)+
    \lambda_eS_{\mathit{ema}}(i,u)+
    \lambda_kS_{\mathit{kg}}(i,q)+
    \lambda_pS_{\mathit{profile}}(i,u).
    \label{eq:hybrid}
\end{equation}
The deployed system uses $\lambda_g=0.20$, $\lambda_e=0.15$, $\lambda_k=0.08$, and $\lambda_p=0.10$; Section~\ref{sec:results} compares these hand-set weights with weights selected on a validation split. The output is a ranked list $R_u=[i_1,i_2,\ldots,i_K]$ in decreasing order of $S(i,u,q)$, returned to the frontend with item metadata and the individual sub-scores.

The algorithm therefore treats the input both as free text and as possible creator intent: high-confidence name matches are preserved, Qdrant supplies broad candidates, user-specific signals are added only for known users, and the bounded sub-scores are returned so that the frontend can explain each recommendation.

\subsection{Backend API and frontend integration}
The backend is implemented with FastAPI, Pydantic validation, and OpenAPI documentation \cite{fastapi}. The main endpoints are \emph{GET /health}, \emph{GET /search/suggest}, \emph{POST /recommend}, \emph{POST /recommend/item}, \emph{POST /interactions}, and \emph{GET /interactions/\{user\}/\{item\}}.

The React frontend provides demo profile login, natural-language search, filters, result cards, score-signal display, similar-item search, a detail view, and feedback controls. It turns the backend into an interactive prototype in which feedback immediately affects later recommendations through EMA.

The API response is transparent: each recommendation contains its metadata, final score, and sub-scores,
\[
    (id,type,title,creators,categories,S,S_{\mathit{sem}},S_{\mathit{graph}},

\]

\section{Experimental Setup}
\label{sec:setup}
The system is evaluated in two ways: an offline ranking benchmark on large public interaction data, which measures every signal of Eq.~\eqref{eq:hybrid} under identical conditions, and scenario tests on the working prototype, which cover the query- and profile-dependent behavior that public logs cannot exercise.

\emph{Datasets.} The offline benchmark uses three categories of the Amazon Reviews 2023 corpus \cite{hou2024blair}: Movies \& TV, Health \& Household, and Industrial \& Scientific. Ratings of four or five stars are treated as positive interactions and all other ratings are discarded. The two large categories are filtered to a 10-core graph (every user and item has at least ten positives) and a random sample of 50,000 users is drawn, after which items with fewer than five remaining interactions are removed; the smaller Industrial \& Scientific category does not survive a 10-core filter and uses the 5-core graph without sampling. Item text (title, category path, description, and store) is taken from the corpus metadata and embedded with the same all-MiniLM-L6-v2 model used by the system. Table~\ref{tab:datasets} lists the resulting graphs.

\emph{Split and candidates.} Each user's positives are ordered by timestamp; the last two form the test set, the one before them the validation set, and the rest the training set. LightGCN is trained on the training set only. Every method ranks the full training catalog, excluding the items already in the user's history, so no negative sampling is involved in evaluation.

\emph{Offline signals.} Public logs contain neither typed queries nor declared profiles, so each signal is replaced by its closest offline counterpart: $S_{\mathit{sem}}$ uses the user's most recent history item as the query, which corresponds to the system's similar-item endpoint; $S_{\mathit{ema}}$ replays Eq.~\eqref{eq:ema_update} over the history in time order; $S_{\mathit{graph}}$ is Eq.~\eqref{eq:graph_score}; and $S_{\mathit{kg}}$ applies Eq.~\eqref{eq:kg_score} with the entities of the user's history (category-path nodes, store, and main category) in place of the query terms, normalized by the candidate's entity count because a history contains far more entities than a typed query. Entities that occur on more than half of the items are dropped as uninformative. The profile score has no offline counterpart and is evaluated only in the prototype scenarios.

\emph{Metrics and baselines.} Recall@$K$, NDCG@$K$, MAP@$K$, and MRR@$K$ are reported for $K\in\{10,20\}$ and averaged over test users. The baselines are most-popular ranking and each signal used on its own (semantic-only, EMA-only, LightGCN-only, and KG-only); the hybrid is evaluated with the hand-set weights of Section~\ref{sec:implementation} and with weights selected on the validation set, and the ablation removes one signal at a time from the selected hybrid. Statistical significance is assessed with a paired Wilcoxon signed-rank test on per-user NDCG@20.

\emph{Weight selection.} The weights of Eq.~\eqref{eq:hybrid} are chosen by grid search on 10,000 validation users, with $\lambda_s\in\{0,0.5,1\}$ for the semantic score and $\lambda_g,\lambda_e,\lambda_k\in\{0,0.05,0.1,0.2,0.4,0.8,1.6\}$, maximizing validation NDCG@20; the test set is used only once, for the selected weights.

\emph{Training settings.} Table~\ref{tab:settings} lists the LightGCN and EMA settings. LightGCN is trained for a fixed budget of 60 epochs without early stopping, so that neither the validation nor the test set influences training; one epoch consists of $\lceil|\mathcal{E}|/B\rceil$ mini-batches. All runs use seed 42 on a single NVIDIA T4 GPU.

\subsection{Prototype scenarios}
The query- and profile-dependent behavior of the deployed system is tested in five scenarios built from the catalog and the demo profiles: actor/director search, singer search, profession-sensitive learning, family-friendly recommendation, and cross-media semantic intent. These scenarios complement, rather than replace, the offline benchmark: they verify that creator matching and KG/profile reranking change the ranking in the intended direction, which the public logs cannot test.

\section{Conclusion and Future Work}
\label{sec:conclusion}
This paper presented a real-time adaptive cross-media recommendation engine built on a unified catalog, Sentence-BERT embeddings, Qdrant vector search, MySQL interaction logging, EMA personalization, LightGCN collaborative filtering, an in-memory knowledge graph, FastAPI services, and a React interface. The final ranking combines semantic similarity, graph compatibility, EMA profile similarity, KG entity overlap, and age- and profession-aware profile matching.
One extensible schema lets movies, books, and music be searched together while still supporting person-specific search over actors, directors, authors, and singers, and shared entities (creators, genres, profile attributes, and interaction history) connect the domains.

The prototype scenarios confirm exact person matching, consistent profile alignment, and cross-domain output in three of five scenarios.
The work has several limitations: metadata quality depends on the source datasets, the knowledge graph is held in memory, the offline benchmark cannot evaluate the declared-profile signal, and multimodal embeddings and fairness- or diversity-aware reranking are not yet included. Future work will enrich metadata through official APIs, move the knowledge graph to a graph database, add domains such as courses and podcasts, and conduct user studies.
